## 2. 「512 MB 闪存」口径澄清（Q3）

| 层级 | 容量 | 说明 |
|---|---|---|
| SPI-NAND 裸片 | 512 MiB | 器件标称 |
| `mtd2 ubi` | 439 MiB | `0x700000 + 0x1b700000` |
| `reserved_bmt` | 66 MiB | 坏块表保留，只读 |
| `rootfs_data`（UBIFS） | **355.4 MiB**（空闲 350.6 MiB） | **唯一可写卷 = overlay** |
| `fit`（只读固件镜像卷） | **24.94 MiB**，镜像 24.91 MiB ⇒ **余量 32 KiB** | **固件本身的空间** |
| UBI 空闲 PEB | **0** | 不能在线扩容 |

> **关键区分**：那 512 MB 里，**可写 overlay 有 350 MiB（运行期装包完全不缺空间）**；受限的是**只读固件镜像卷 `fit`**。所以「把能力预装进固件」受 32 KiB 约束，而「运行期安装」不受。两条路都已按用户选择实现（D4 + D5）。

## 3. 架构 A vs C：为什么选 C

### 3.1 硬件加速：**逐字节等价**
决定 offload 的只有两件事：**判定在哪一层**、**抓哪些流进用户态**。A 与 C 都是「内核 nft：`@proxy_hosts` 且目的 ∉ `@china_ip4` → 抓；其余走原 `forward` → `flow add @ft`」。
**fake-ip 只是 DNS 应答，不是路由机制**，进不了这个判定。

⇒ 两架构下 `cat /sys/kernel/debug/ppe/bind | wc -l` **必须是同一个数**（已写成验收判据，见 `04` §3.2）。

### 3.2 代理侧软件性能：C 更好
| 指标 | A | C |
|---|---|---|
| 每连接用户态开销 | 必须 sniff TLS ClientHello 才知道域名 | 目的 IP 即 fake-ip，查表即得域名，**零嗅探** |
| DNS 首答（非 CN） | 每次等真实上游 | **直接合成 `198.18.x`，不等上游** |
| UDP/QUIC 分流 | 只能 sniff；ECH 场景失效 → 退 IP 规则 | 域名→fake-ip 映射，**精确** |
| 加密吞吐 | 同（同一 sing-box / ChaCha20-Poly1305 标量路径 / ~578 Mbps 单核参照） | 同 |
| 故障域 | 无新增 | 名单客户端多一个 DNS 依赖 → **guard + fail-open 兜住** |

**结论：按「性能优先」⇒ 架构 C。**

### 3.3 架构 C 的硬前提
> CN 域名在名单客户端侧**必须回真实 IP**。若被 fake-ip 化，客户端拿 `198.18.x`，内核 `ip daddr @china_ip4` 匹配不到真实 CN 目的 IP ⇒ 内核放行失效、CN 流量被拐进用户态 ⇒ **offload 全丢**。

## 4. `fit` 扩容尺寸：为什么不硬编码

用户选择「大扩：sing-box + netbird 都预装」。但**不需要、也不应该**写死一个 "+88 MiB" 常数：

- HTTP U-Boot 恢复页在**上传固件时**才决定 `fit` 卷尺寸（`round_up(镜像大小)`），`rootfs_data` 自动吃剩余；
- 因此**实际尺寸由构建产物的 `.manifest` 安装体积决定**；
- CI 只做「比上一版大 ⇒ release notes 标注需重刷」的提醒（`00-总纲` §4.5）。

**已知代价（用户已接受）**：每次升级固件多写 ≈镜像大小的数据到 2.26 MB/s 的 NAND；`rootfs_data` 被相应压缩；netbird 二进制随固件版本回退。

## 5. Q14 的源码实证：HTTP U-Boot 能自动扩容

仓库：`YYH2913/http-uboot`（`master`），文件：`net/lwip/httpd_recovery.c`

```c
static const struct recovery_ubi_layout recovery_ubi_layouts[] = {
    { "2.0", "ubi" }, { "1.5", "ubi1.5" }, { "1.0", "ubi1.0" },
};

// 只保留这三个卷；XR1710G 的 factory 在白名单里
static bool recovery_preserve_ubi_volume(const char *name) {
    if (!strcmp(name, "ubootenv") || !strcmp(name, "ubootenv2")) return true;
    if (of_machine_is_compatible("gemtek,xr1710g-ubi")) return !strcmp(name, "factory");
    ...
}

// 上传固件主流程：先 remove 除白名单外的所有卷（含旧 fit 与 rootfs_data）释放 PEB
recovery_cleanup_ubi_firmware(&target, status_leds, image_size);

// 卷不存在 → 按 image_size 创建；镜像变大 → resize
if (!target.cur_size)              recovery_create_ubi_target(&target, image_size);
else if (image_size > target.cur_size) recovery_resize_ubi_target(&target, image_size);
   // → ubi_resize_volume(desc, DIV_ROUND_UP(new_size, vol->usable_leb_size))

// rootfs_data：size=0 ⇒ 吃掉剩余全部 PEB
recovery_ensure_rootfs_data(&target);
```

**结论**：
1. ✅ **上传更大的 `*-sysupgrade.itb` 即自动扩容 `fit`** —— 不需要新 installer、不需要改 DTS、不需要 `ubirsvol`；
2. ⚠️ **该路径会连 `rootfs_data` 一起删** ⇒ **每次恢复页刷固件都清空 overlay/配置**（白名单里没有它）—— 刷前必须备份 `/etc/config`；
3. ⚠️ 布局选择器必须选 **UBI 2.0**（`part="ubi"`，对应 `mtd2` `0x1b700000`）。

## 7. 术语（本轮新造，需同步进 `CONTEXT.md`）

| 术语 | 定义 |
|---|---|
| **offload 不变量** | `chain forward` 的 `flow add @ft`、flowtable 设备表、`flow_offloading*` 三者永不被代理/组网代码触碰 |
| **内核态分流** | 分流判定发生在 nft / 策略路由层；只有被内核放行的流量才离开快路径 |
| **CN 放行集合** | `china_ip4` / `china_ip6` nft interval 集合（快照 + 运行期更新 + `dnsmasq --nftset` 注入） |
| **名单客户端** | `@proxy_hosts` 中的源地址；只有它们会被捕获进用户态 |
| **假 IP 作用域** | fake-ip 只允许投递给名单客户端；普通客户端恒为真实 IP |
| **fail-open** | sing-box/DNS 不健康时撤掉抓取与劫持规则，名单客户端退回直连，而非断网 |
| **恢复页重建布局** | HTTP U-Boot 恢复页上传固件时移除白名单外的 UBI 卷并按镜像大小重建 `fit`；副作用 = 清空 overlay |
