# 01 — 方案一：官方 sing-box 核心 + 自写内核 CN 放行集合 + 自写极简 LuCI

> 上游：`plan/00-总纲-架构与供给链.md`（不变量 I1–I4、nft/uci/路由数据模型）
> 依据：`research/APP-FIT-RESEARCH-2026-09-10.md` §9.6 / §9.8 / §9.9

## 1. 目标与判据

| 判据 | 内容 |
|---|---|
| P1-1 | 名单客户端能按「CN 直连 / 其余走代理」分流，且 CN 直连流量的 PPE/NPU 卸载**完整保留** |
| P1-2 | 非名单客户端的解析结果、吞吐、`ppe/bind` 计数在开/关两个状态下**无实质差异** |
| P1-3 | 非名单客户端**永不接触 fake-ip**（解析 `www.google.com` 必须得真实 IP） |
| P1-4 | 零新 kmod 依赖路径成立（`kmod-tun` 已内置，F6） |
| P1-5 | 不变量 I1–I4 全部满足 |

## 2. 为什么不是 homeproxy、为什么不用 TProxy

| 项 | 事实 | 结论 |
|---|---|---|
| homeproxy 依赖 | 硬依赖 `+kmod-nft-tproxy` + `+sing-box +firewall4 +ucode-mod-digest`；且**不在 OpenWrt 官方 feed**（在 ImmortalWrt luci feed） | 引入 = 第三方 feed + 锁源义务 |
| homeproxy 分流层 | 默认 `routing_mode=bypass_mainland_china`，CN 判定生成在 `generate_client.uc`（`rule_set: 'geosite-cn' → route`）——**用户态执行**；`firewall_pre.uc` 只生成抓取规则、不做目的判定 | **先天不保 CN 流量的 offload**（除非自己再叠内核放行链） |
| TProxy 可用性 | 本机**没有 `nft_tproxy.ko` / `nf_tproxy*`**（F6），nft `tproxy` 语句不可用 | TProxy 形态今天不可用 |
| 可用替代 | `kmod-tun` **已内置**；`nft_redir.ko` / `nft_nat.ko` 在 | 走 **TUN 入站**（DNS 用 `redirect` 做本地投递） |

⇒ 前端自写（`luci-app-xr1710g-proxy`），核心用官方 `sing-box`。

## 3. 数据流（架构 C）

```
LAN 客户端
 ├─ 非名单（绝大多数）
 │    :53 → dnsmasq（真实 IP）→ 路由 → chain forward → flow add @ft → PPE/NPU    ← 完全不受影响
 └─ 名单（@proxy_hosts）
      :53 → nft(inet xr1710g_proxy, nat dstnat-5) redirect → sing-box DNS:5333
             ├─ CN 域名（geosite-cn 规则集）→ 真实上游 → **真实 IP**（保证 @china_ip4 能匹配）
             └─ 其余                        → fakeip(198.18.0.0/15)
      数据：prerouting(mangle) 判定
             ├─ ip daddr @china_ip4 / ip6 daddr @china_ip6 → accept（直连，**保 offload**）
             └─ 其余 → meta mark 0x40 → ip rule 0x40/0x40 table 100 → default dev singtun0
                        → sing-box（**无需 sniff**，fake-ip 反查即得域名）→ 出站节点
```

**关键点（研究 §9.8 点名的坑）**：若名单客户端的 CN 域名也被 fake-ip 化，客户端拿到 `198.18.x`，内核 `ip daddr @china_ip4` **匹配不到真实 CN 目的 IP** → 内核放行失效、CN 流量被拐进用户态 → offload 全丢。所以 **CN 域名必须回真实 IP**，这是架构 C 成立的前提，也是 §4.3 配置生成的硬约束。

## 4. 实现分解

### 4.1 nft 规则集（`nft/template.nft` → 渲染 → `nft -f`）
见 `00-总纲` §2.2。要点：
- 独立表 `inet xr1710g_proxy`，**绝不写 `inet fw4`**（I3）；
- `set` 用 `flags interval`；
- 载入用单 batch（保证原子）；
- `stop` 用 `nft delete table inet xr1710g_proxy` 精确回收。

### 4.2 策略路由（`init` 内）
- 启动前冲突检测：`ip rule show` 里若已存在 `0x40/0x40` 或 table 100 的他方条目 → 拒绝启动并落日志（F9 已知 Tailscale 用 `0x80000/0xff0000` + table 52）；
- 添加 `ip rule add fwmark 0x40/0x40 table 100` + `ip route add default dev singtun0 table 100`；
- `stop` 逐条删除自建条目，不动他人。

### 4.3 sing-box 配置生成（`/tmp/xr1710g-proxy/config.json`）

```jsonc
{
  "log": { "level": "warn", "output": "/tmp/xr1710g-proxy/sing-box.log" },
  "dns": {
    "servers": [
      { "type": "udp",    "tag": "cn",     "server": "223.5.5.5", "detour": "direct" },
      { "type": "fakeip", "tag": "fakeip", "inet4_range": "198.18.0.0/15" }
    ],
    "rules": [
      { "rule_set": "geosite-cn", "server": "cn" }      // ← 硬约束：CN 域名回真实 IP
    ],
    "final": "fakeip"
  },
  "inbounds": [
    { "type": "tun", "tag": "tun-in", "interface_name": "singtun0",
      "address": ["172.19.0.1/30"], "stack": "system", "mtu": 1500,
      "auto_route": false,        // ← 绝不全局接管
      "auto_redirect": false }
    // DNS 由 dns.listen 监听 :5333（由 nft redirect 投递），不另开 inbound
  ],
  "outbounds": [ /* 用户节点 + direct */ ],
  "route": {
    "auto_detect_interface": true,                        // 防环
    "rules": [ { "protocol": "dns", "action": "hijack-dns" } ],
    "final": "proxy",
    "rule_set": [ /* geosite-cn → direct, geosite-geolocation-!cn → proxy, ... */ ]
  },
  "experimental": { "cache_file": { "enabled": true, "path": "/tmp/xr1710g-proxy/cache.db" } }
}
```

**四条硬约束**：
1. `dns.rules` 必须把 CN 域名指到**真实上游**（架构 C 的前提）；
2. `auto_route` / `auto_redirect` **必须 `false`**（研究 §9.3 反模式 ①：全局接管 = 全部流量进用户态）；
3. 所有可变路径（`cache_file` / 日志 / 远程 `rule_set` 缓存）**必须在 `/tmp`**（G2 零 NAND 写）；
4. `route.auto_detect_interface: true`（防路由环）。

### 4.4 CN 放行集合（`scripts/xr1710g-cn-list.sh` + 运行期更新）

- **快照**：构建前由脚本抓取 → 校验（格式 / 条目数 / 去重）→ 生成 `china_ip4.txt` / `china_ip6.txt` → 随包装入只读 squashfs（`/usr/share/xr1710g-proxy/`）。
- **运行期更新**：`global.cn_list_update=1` 时定时抓取到 `/tmp` → 校验 → **单 batch 原子换集合**（`nft flush set` + `add element`）；校验失败则保留旧集合。
- **域名级补充**：`dnsmasq --nftset=/<域名>/china_ip4`（F7：本机 dnsmasq 2.93 编译含 `nftset`、**无** ipset ⇒ 只能用 nft 集合）。
- **无 RTC 保护**：时钟不正常时只用快照，不阻塞启动。
- **实施首步先取证**：名单源 URL + 许可证 + 更新频率 + 实测条目数 → 记入 `docs/FIXES.md` 后再固化（`00-总纲` §6 风险项）。

### 4.5 守卫（guard）与 fail-open

| 触发 | 动作 |
|---|---|
| `sing-box` 进程不存在 / 健康检查失败 | 撤 `dns_redirect` 表 + `capture` 表 + 删 ip rule/route → 名单客户端退回**直连 + dnsmasq** |
| procd 重启计数超阈 | 进入 fail-open 并**停止 respawn**、落明确日志 |
| `/tmp/xr1710g-proxy/state` 时间戳 | 防抖（避免抖动期间反复建/撤表） |

> fail-open（而非 fail-closed）= 与 G4「失败不影响正常网络」一致；代价是名单客户端在故障期直连（方向安全但不代理），必须在状态页明示。

### 4.6 极简 LuCI（`packages-xr1710g/package/luci-app-xr1710g-proxy/`）

| 区块 | 内容 |
|---|---|
| 总开关 | 读写 `global.enabled`；切换 = `uci commit` + `/etc/init.d/xr1710g-proxy reload`（**绝不触发 fw4**） |
| 名单 | 编辑 `global.proxy_hosts`（IP / CIDR） |
| CN 名单 | 显示快照条目数与时间；「立即更新」按钮 |
| 状态 | sing-box 进程状态、DNS guard 状态、`ppe/bind` 计数、当前 fwmark/table、fail-open 提示 |

- `uci-defaults` 只写默认值（`enabled=0`），**不 enable 任何服务**（I4）。

## 5. 与其它方案的交互

| 交互 | 结论 |
|---|---|
| 与 Tailscale（已在跑） | 名单客户端若同时是 Tailscale 节点，需注意 `0x80000/0xff0000` 屏蔽；本轮只做**冲突检测 + 拒绝启动**，不做合并策略 |
| 与方案二 netbird | 两者可共存；netbird 的 `wt0` 隧道流量走 CPU（其自身特性），不占用本方案的 fwmark/table |
| 与将来 pbr/mwan3 | 本方案占用 `0x40` + table 100；上 pbr 必须重审（登记在 `02-方案二` §4 与 FIXES） |

## 6. 本方案的验收要点（细则见 `04-验收与测试矩阵.md`）

- **A/B 对照**：开关前后，非名单客户端 `ppe/bind` 计数与 iperf3（≤2%）；
- **DNS 作用域**：非名单客户端解析结果**绝无 `198.18.x`**；名单客户端 CN 域名得真实 IP；
- **失败演练**：`kill -9 sing-box` 后非名单客户端无感；
- **净身归还**：卸载后 `nft list ruleset` / `ip rule show` / `uci show` 与基线逐字节 diff 为空。
